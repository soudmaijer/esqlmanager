# eSQLManager

Java Swing database manager (originally an Errorsoft graduation project, 2002-2003), modernised to run on Java 25 with Maven. It manages MySQL and PostgreSQL; SQL Server and Oracle have a dialect for browsing only.

## Build, run, test

* Maven wrapper only (`./mvnw`), never Gradle. Java 25 (`maven.compiler.release`), sources are UTF-8.
* Run: `./mvnw compile exec:exec` (starts `nl.errorsoft.esql.Main` with `runtime/` as working directory, see Configuration below).
* Validate locally: `./start.sh` starts a PostgreSQL 17 container (`esql-pg`, user `postgres`, password `test`, sample database `shop`, on the first free port from 5432, the script prints it) and the application, `./start.sh --db-only` only the database, `./stop.sh` removes the container.
* Distribution: `./mvnw -Pjlink package` builds `target/runtime-image` (`src/package/jlink.sh`: `jdeps --print-module-deps` on the classes and `target/libs`, plus a fixed list of modules that are loaded by name such as `java.naming`, `jdk.crypto.ec`, `jdk.localedata`, with `--include-locales=en,nl,de,fr,es` (jdk.localedata is the biggest module; the rest is the closure the downloadable MySQL and Oracle drivers need); `--strip-debug --compress zip-9`). `./mvnw -Ppackage package` runs jpackage (`src/package/jpackage.sh`) into `target/dist`: an app image by default, `-Djpackage.type=dmg` for an installer; version is the pom version without `-SNAPSHOT` padded to three parts. Both profiles first delete `target/libs`, `target/runtime-image` (and `target/dist`) in `prepare-package`, so a stale jar never ends up in the installer. Both profiles activate only when named, the default build is untouched. Do not run them for `verify`.
* Working directory of a packaged app: code reads `conf/...` and `credits.txt` through `app.DataDirectory.file(...)`. Without the system property `esql.seed` that is the working directory (development, tests, `exec:exec`). jpackage starts the app with `-Desql.seed=$APPDIR/seed` (a copy of `runtime/` inside the bundle), and the data directory is then `~/.esqlmanager`, where missing files are copied from the seed. This is needed because a Java process cannot change its working directory (a `user.dir` option does not affect relative file opens), a Finder-launched app starts in `/`, and the bundle must not be written to. New code that opens a file under `conf/` uses `DataDirectory`, never a plain relative path.
* Test: `./mvnw test`. The tests start Postgres 17 and MySQL 8 with Testcontainers and are skipped without Docker.
* A GUI cannot be started inside the Claude sandbox (no display). Run harnesses with the sandbox disabled, and verify UI work by painting the root pane to a `BufferedImage` in-process.

## Finishing a change

* Update `README.md` and `changelog.txt`, and retake `docs/screenshot.png`, `docs/designer.png`, `docs/query.png` and `docs/connect.png` when the UI changed, before reporting a change as done.

## Design decisions

### Database differences live in a Dialect

* `dialect/Dialect` is the single place that knows how a server differs: quoting, string literals, DDL for tables, columns and indexes, paging, switching database, listing databases and tables, table maintenance, and exporting a table definition. `AbstractDialect` holds ANSI/JDBC-metadata behaviour, `dialect.mysql.MySqlDialect` and `dialect.postgres.PostgresDialect` override what differs. Type names that differ per server go through protected hooks of `AbstractDialect` (`identityType`, `isAutoIncrement`, `ddlTypeName`, `plainDefault`, `isSizedText`, `datatypeName`); the PostgreSQL mapping (`int4` to `integer`, serial and identity columns, `::` casts in defaults) lives in `PostgresDialect`.
* A dialect never runs SQL and takes no `DatabaseConnection`: it writes statements (strings, or small records such as `MaintenanceStatement` and `GrantQuery`) and maps result or metadata rows to domain objects (`readTable`, `readProcess`, `readColumn`, `columnDdl`, `UserAdmin.readUser`, `readGrants`). Lookups it needs the answer of are queries the repository runs first and hands back (`tableTypeSql` before `checkForeignKeyTable`, `autoNumberedColumnsSql` before `afterDataLoadSql`, the primary key name for `dropIndexSql`). Repositories execute them, `AbstractRepository.listTables` and `queryStrings` hold what several repositories share.
* Callers ask the dialect. Never branch on the server type (`if type == MY_SQL`) outside `dialect`. Adding a database means adding a `Dialect`, a `<driver>` section in `runtime/conf/datatypes.xml`, and a case in `DialectFactory.forType`.
* Optional functionality is declared with `Dialect.supports(Feature)`; the controllers show a message when a feature is missing.
* `UserAdmin` (per dialect, from `Dialect.getUserAdmin()`) writes the SQL of account and privilege management, `UserRepository` runs it. MySQL accounts are `user@host` and privileges are GRANT/REVOKE; PostgreSQL accounts are roles, global privileges are role attributes, database and table privileges come from the object ACLs.
* PostgreSQL has one database per connection: `Dialect.databaseSwitch()` is `RECONNECT`, so `DatabaseConnection.useDatabase` connects again (MySQL and SQL Server set the catalog, Oracle does nothing). Dropping the database in use first moves to the one `databaseToLeaveFor` names. The profile's database selection is a filter, and its first entry is the database to connect to (default `postgres`). Unqualified names resolve to `current_schema()` (`currentSchemaSql`, run once by `DatabaseConnection.getSchema`).
* Schemas: a dialect with `Feature.SCHEMAS` (PostgreSQL) has a tree of server > databases > schemas > tables, like DBeaver; MySQL stays server > databases > tables. Opening a database node connects to it and lists its schemas (`Dialect.listSchemasSql`, system schemas `pg_catalog`, `information_schema`, `pg_toast*` and `pg_temp*` left out). `database.Schema` sits between `Database` and `Table`; a `Table` knows its schema (null on MySQL, or when the current schema is meant). Every statement on a table uses `Dialect.quote(TableName)` (`table.TableName`, from `Table.qualifiedName()`), which writes `"schema"."table"`; table taking `Dialect` methods take a `TableName`. Menu labels and messages take the words from `Dialect.databaseTerm()` and `schemaTerm()` (`TreeMenu.Item.label(dialect)`: "Reload schemas" on a PostgreSQL database node), never a server type check.
* Which databases and schemas a profile shows is a `connection.DatabaseSelection` (pure record: insertion ordered map of database to selected schemas, an empty set means all schemas, an empty selection shows everything; `showsDatabase`, `showsSchema`, `parse`/`toCsv`, `withDatabase`/`withSchema`; database names compared ignoring case, names with a comma refused). `ConnectionProfile.getSelection()` is the truth, `getDatabases()`/`setDatabases` are the CSV view that `Dialect.getConnectionDatabase` and `copyAs` use. `connection.ProfileXml` reads and writes a `<profile>` element (DOM, testable without the file): `<databases>` stays, `<schemas><database name><schema>` is optional and written only for databases with chosen schemas, schemas of a database that is not selected are dropped on read. `DatabaseService` takes the selection (`ConnectionContext` passes `profile.getSelection()`) and `getDatabases`/`getSchemas` apply it, so everything must ask the service; `ExportRepository.tableNames` stays unfiltered on purpose (a whole-database export includes unticked schemas, the export dialog notes it) and `DatabaseService.properties` counts tables over the shown schemas.
* The connect dialog (`connection.ui.dialog.ConnectionProfileDialog`) has two tabs. The "Databases and schemas" tab (`connection.ui.DatabasePickerPanel`, a `ui.component.CheckBoxTree` with a `CheckBoxTree.CheckModel`) is enabled only after Test connection succeeded. `ConnectionProfileController` owns one scratch `database.DatabaseListService` (unfiltered database and schema lists, one connection moved with `useDatabase`) and one single-thread virtual executor per test, a generation counter bumped by `invalidate()` (settings changed, new test, dialog closed) so answers that arrive late are ignored, and closes the connection through the same executor. Ticks live in the picker's `DatabaseSelection` and survive clearing the tree; databases the server does not have are dropped when the selection is read after a listing. A dialect without `listDatabasesSql` (Oracle) lists the profile's own databases.
* The primary key index is always presented as `PRIMARY`, whatever name the server gave it. `Dialect` methods take the quoted/unquoted name and quote it themselves.

### SQL safety

* Identifiers go through `dialect.quote(...)`, values through `dialect.literal(...)` (or `DatabaseConnection.formatFieldValue`, which delegates to it). Never concatenate a raw name or value into a statement. MySQL escapes backslashes in literals, PostgreSQL does not, which is why this is per dialect.
* Column types and lengths are text from the user or a model file: `AbstractDialect.typeWithLength` accepts a plain type name and a length of digits (`10,2`), and writes the values of ENUM and SET through `literal`; MySQL accepts only an engine of `getTableTypes()`. Anything else is an `EsqlException`.
* Metadata lookups use `PreparedStatement` parameters.
* An empty cell is SQL `NULL`, not the text "null" (`TableCell.isNull()`; `getData()` and `getNativeData()` are null for NULL and `ui.table.NullCellRenderer` draws a dimmed NULL): editing writes NULL for an empty text, and a NULL cell opens empty in an editor (`TableCell.getEditText`).
* Paging on PostgreSQL and MySQL orders by the primary key so that rows do not move after an update.
* A script written by Export switches database with `\connect` on servers that cannot do it in SQL; Import understands it.
* Every `TableRepository` statement on a table starts with `useDatabaseOf(table)`: the connection is shared with the query tabs, which may have moved it to another database (contract test `tableStatementsRunInTheTablesDatabaseWhateverTheConnectionUses`).
* `DatabaseConnection.executeQuery` closes its statement when execution throws; otherwise the statement closes with its result set.

### UI

* Look and feel is FlatLaf, chosen through `settings.Appearance` (Follow the system, Light, Dark, Native) and stored in `conf/settings.xml` (`<appearance>`), changed in Settings > Preferences and applied at once. On macOS FlatLaf uses its Mac themes, `Main` sets the screen menu bar and system appearance properties before the first window (`Appearance.prepareDesktop`). The native macOS look was far too slow when resizing, so it is only used when the user picks Native.
* Use Swing only, no AWT widgets (`Label`, `Button`, ...). Dialogs use layout managers, not null layouts with absolute bounds; `ui.util.Forms` gives the 12px padding, the button row at the bottom right, titled groups and a label/field grid. Only the designer canvas (`DesignerCanvas`, its cards, the text inside a `NoteCard`) and the splash (the credits area on the drawn splash) place components at absolute positions.
* Do not hardcode `Color.white` or `Color.gray`. Take colours from `UIManager` (grid lines `Table.gridColor`). A read-only `JTextPane` is painted grey by FlatLaf, set its background explicitly. A problem or success message takes `Forms.errorColor()` / `Forms.successColor()` (the theme's `Actions.Red`/`Actions.Green`, one fallback each).
* The help (`help.ui.HelpPanel`, shown by `help.ui.HelpWindow`, a work window with its own tab in the window bar like the views of a connection; `MainWindow.showHelp` opens it or brings the open one forward, it needs no connection; the Help button, the Help menu item) renders the Markdown of docs/ with `HelpPages.render(name, dark)`: a white page in light themes, a dark one in dark themes (the pane takes its background from the same `HelpPages.LIGHT_BACKGROUND`/`DARK_BACKGROUND`), rendered again when the look and feel changes.
* Settings has only the appearance; there is no auto-update.
* Swing is touched on the event thread, the start up included (`Main` creates the `MainController` with `invokeLater`). The splash (`app.ui.SplashWindow`, 560x340, drawn: the logo SVG at screen scale on a fixed dark gradient, name, version and commit from `BuildInfo`, a status line, the copyright; fixed colours, it is artwork and not themed) and the credits (`CreditsPanel`, scrolling in the splash opened from About, which closes on a click, Esc, Enter or Space) are `JComponent`s that paint in `paintComponent`; the splash is shown with `invokeLater` after the main window, and its closing timer starts on `windowOpened`. `MainWindow.print` and `setStatusInfo` marshal themselves with `invokeLater`.
* The query editor is an `RSyntaxTextArea` (com.fifesoft) in an `RTextScrollPane` with SQL highlighting, line numbers and the library's undo. `ui.editor.EditorTheme.install` gives it the RSyntaxTextArea theme `idea.xml` or `dark.xml` matching `FlatLaf.isLafDark()` and applies it again when the look and feel changes.
* The SQL query is a work window of its connection (`query.ui.QueryTab`, a `JPanel`, opened by `ConnectionWindowController.startQueryTab` through `ConnectionView.showQueryTab`, numbered per connection "Query", "Query 2", ...). Its controller `query.control.QueryController` runs statements on a virtual thread (the run buttons are disabled and the status bar says "Running..." meanwhile; stops at the first error, reports it through `ErrorHandler` naming the statement) and hands back, on the event thread, a `QueryController.RunResult` with a `StatementResult` per statement with rows (a `table.QueryResult` from `TableService`, data only), which `QueryTab` shows in a `TableDataTab` it builds as a closable result tab (title the statement, tooltip the full text, a line with time, database, rows and duration; at most 20). On a dialect with `Feature.SCHEMAS` the toolbar has a schema picker next to the database (labelled with `Dialect.schemaTerm()`); `QueryController.useSchema` sets it through `QueryService.useSchema` (`DatabaseConnection.useSchema`), applies it again before every run because the connection is shared, and the completion resolves plain names in it. Changing the database or schema runs through `inBackground` (its overload with an `always` callback) with the pickers and run buttons disabled until it is done; the completion loads the columns of a table on a virtual thread at the first ask and offers none until they arrive. It implements `query.SchemaNames` for the completion, caching the tables (loaded on a virtual thread when the database is chosen) and the columns per tab. Closing the tab calls `QueryTab.close()`, which uninstalls the completion; the `EditorTheme` listener goes when the editor stops being displayable.
* Table data (`table.ui.TableDataTab`): editing a cell in the grid writes it when the edit stops; "Update changes" is enabled only for what `table.PendingChange` (pure) finds pending (a grid edit or the value editor with a text that differs, `TableCell.isChangedBy`, or a new row). The value of one cell is edited in `table.ui.CellValueEditor` below the grid (F2, double click, the pencil or the cell's context menu): an `RSyntaxTextArea` with the style of `table.ValueFormat.detect` (JSON, XML, SQL, plain; pure, also pretty prints JSON and XML, XML without a DOCTYPE), Apply and Revert only when changed, read only with a hint when the view is not a table, Upload/Download through the blob dialogs for a binary column (blobs are not loaded into the grid). Only a table view has `setRowEditing(true)`.
* `query.SqlScript` splits a script on `;` outside quotes, dollar quotes and comments and finds the statement at the caret; `query.SqlContext` is a small tokenizer that tells what fits at the caret (tables, columns of an alias or table, anything) and resolves aliases. Both are pure and unit tested.
* Completion uses the RSyntaxTextArea AutoComplete library (`com.fifesoft:autocomplete`, the release that matches rsyntaxtextarea), with `query.ui.SqlCompletionProvider`. Names that are not plain lower case identifiers go through `dialect.quote`.
* Query shortcuts: menu key (Cmd/Ctrl)+Enter runs the selection or the statement at the caret, +Shift+Enter runs all, +E explains it; Ctrl+Space, Meta+Space and menu key+Shift+Space open the completion (macOS reserves Cmd+Space for Spotlight unless the user turns that off).
* The explorer (`connection.ui.ExplorerPanel`, left of the desktop in a horizontal split) is one tree with a hidden root: a `ConnectionNode` per open connection with its `database.ui.ConnectionBranch` below it, then a grey `ProfileNode` per saved profile that is not connected (drawn like a connection with an expand handle: expanding it, a double click or Connect connects it, a will-expand listener vetoes the expansion because the `ConnectionNode` takes its place at once; Edit connection opens the profile dialog on it; `MainController.refreshProfiles`). Selecting a node only selects it (and activates its connection), it never loads or opens anything. The explorer's branches are lazy (`new ConnectionBranch(tree, node, true)`): a database, schema or table gets a `ConnectionBranch.Loading` child ("Loading...", `needsLoading`), and the will-expand listener asks `ConnectionWindowController.loadChildren(node, always)` to load it (schemas or tables of a database, on PostgreSQL connecting to it; tables of a schema; columns of a table). `connection.NodeLoads` (pure, identity) keeps a node from loading twice, the controller's `inTree` runs the JDBC of tree loads under one lock per connection (shared connection, PostgreSQL reconnects), and after a failure (reported by `inBackground`) the node collapses again. The dialogs' trees (`DatabaseTree`) are not lazy. A load in a branch only moves the selection when it was on or below the loaded node. Its toolbar starts with Connect (connects the selected saved profile, else opens the connection dialog), then New query, User manager and Open in designer, enabled for the selected node through `TreeMenu.missing` (New query, also Tools > New query with menu key+T, only inside a database; `ExplorerPanel.missing/supported` and `addStateListener` let `MainWindow.updateMenus` follow the selection); table and column actions (create and drop table, add and drop column) are only in the tree's context menus; the main toolbar at the top right has only Help and Preferences, Disconnect is in the connection's context menu. The tree's own toggle on double click is off (`setToggleClickCount(0)`): `doubleClicked` opens a table without expanding it and toggles other nodes (expanding loads); Enter opens a table's data or the table list of a database or schema (`ConnectionWindowController.openTableList`, also Show tables in their context menus). The table list (`table.ui.TableListTab`) has a toolbar: Add table, Reload, New query, and for the selected rows Open data, Edit table, Indexes, Drop table and a wrench drop down with `TreeMenu.maintenanceItems`; `TreeMenu.missingForTables(item, rows)` enables open and edit for one row, drop and maintenance for one or more, and the actions go to table-taking controller methods (`showEditTableTab(Table)`, `dropTables`, `maintainTables`, `showCreateTableTab(Database, Schema)`, `startQueryTab(Database, Schema)`). A table data tab has "New query on this table" (`ConnectionWindowController.startQueryTab(Table)`, `QueryController.startInSchema`). Columns show their type in grey after the name (`TableColumn.getTypeLabel`, the dialect's `datatypeName`), the key icon for the primary key, the Lucide link-2 icon (`foreign-key.svg`) for a foreign key, and a tooltip with not null, default and auto increment.
* What an action works on comes from the node selected in the explorer through `connection.TreeSelection` (pure, null when nothing is selected; `ConnectionView.selectedObject` returns the selected node only when it belongs to that connection, `getDatabase/getSchema/getTable/getTableColumn` delegate to `TreeSelection`). `ConnectionWindowController` asks for it with `selectedDatabase(action)`, `selectedTable(action)`, ... which warn "Select a table in the tree first." and return null. A query tab opened without a selection starts on the database the connection uses (`QueryController.startDatabase`, reached from code only, the UI needs a database selected).
* Contextual buttons (rule U9): an action that cannot run in the current context is disabled and its tooltip says what is needed (`ToolbarButtons.setAvailable(component, missing)`: "New query: select a database first."); an action the server never offers (`TreeMenu.supported(item, dialect)`, from `Dialect.supports` and `maintenanceCommands`) is hidden, as are row buttons on views that can never be edited (query results, server status). Toolbar, menu bar and context menus take the decision from the pure `TreeMenu.missing(item, path, dialect)`/`supported` so they never disagree.
* Context menus are built when they open and show only the items that apply. The tree's items come from `connection.TreeMenu.itemsFor(node, dialect)` (pure, `TreeMenuTest`), based on `Dialect.supports(Feature)` and `Dialect.maintenanceCommands()`; `ExplorerPanel.perform` wires each item to a `ConnectionWindowController` method. The designer's menus are built in `DesignerCanvas` (canvas, table, database, note, connector; `DesignerCanvasMenuTest`). Popups open on `isPopupTrigger()` in both mousePressed and mouseReleased, after selecting what is under the cursor.
* Create table, Edit table and Indexes are work windows of their connection (`table.ui.TableEditorTab`, `table.ui.IndexesTab`, opened by `TableEditorController` and `IndexesController` through `ConnectionView.showEditorTab`), one per table under a key (`selectEditorTab` jumps to an open one), titled "New table", "Edit orders", "Indexes orders". Save and Cancel are at the bottom. An editor implements `ui.component.EditorTab`: `ConnectionView.closeTab` (also the tab's close cross) asks its `confirmClose()` ("Discard changes?" when modified), `removeTab` closes it without asking after a successful Save. Esc does not close a tab (`EscapeToClose` is for dialogs). The field properties of one column (`ColumnPropertiesDialog`) and the name prompt for a new index stay dialogs.
* Work windows are internal frames on the desktop of the main window (`JDesktopPane`): every view of a connection (table data, table list, query, editor, indexes) is a `connection.ui.WorkFrame` (the server icon of its connection, its own bar at the bottom with the view's last message and the paging of table data), registered per connection by `connection.ui.WorkFrames` (the `ConnectionView` of a connection; table data and lists are found again by a key and replaced in place), plus designers and the help. A tab title is the view's ("orders"), with the profile name of its connection behind it (" (local pg)") when two open tabs share it (`WindowTabsPanel.CONNECTION_TITLE`); a connection is titled by its profile name (`ConnectionWindowController.getTitle`), so two connections as the same user@host are told apart. The table data has a toolbar at its top to insert, delete and save rows, enabled only for a table (`TableDataTab.setRowEditing`). They are always maximized and have no title bar or border (`app.ui.WindowTabsPanel` removes the UI delegate's north pane, again after a change of look and feel); their menu bar (the designer's) stays inside the frame. `WindowTabsPanel`, a `JTabbedPane` with empty content above the desktop, has a tab per window with its frame icon (the server's brand icon, the designer icon) and title (kept in sync); selecting a tab selects the frame, an activated frame selects its tab, the close cross or a middle click calls `doDefaultCloseAction` so the frame's own close path asks (Disconnect / save), and `MainWindow.removeWorkFrame`/`removeDesignerWindow` remove the tab. The Window menu lists Next/Previous window and the open windows grouped under the name of their connection (help and designers without a connection last) (menu key+Shift+] and [). There is no tiling or cascading. No feature opens a separate top level window for its work; dialogs stay dialogs.
* README and docs screenshots are taken in the light appearance only.
* Destructive actions (create and drop database) are in the context menus of the tree, not in the explorer toolbar. Disconnecting (`ConnectionWindowController.disconnect`) first asks each editor with changes, then "Disconnect from <profile>? N tabs will close." (Disconnect / Cancel); the work windows of the connection close, its designers stay open without a connection (`DesignerWindow.detach`, the server type is kept in the designer) and Generate then asks for an open connection to the same kind of server.
* The top row of the main window holds the window tabs (`app.ui.WindowTabsPanel`, filling the width, 32px) on the left and, behind a thin vertical `JSeparator`, the toolbar on the right: Connect and Disconnect, a second separator, then Help (`MainWindow.showHelp`) and Preferences (Lucide ellipsis, opens the same dialog as the menu item).
* The main window is a vertical split: on top the explorer and the work area (window tabs and desktop) in a horizontal split, below them one output panel across the whole width, then the status bar. Without connections and saved profiles the explorer shows a hint with a "New connection..." button; the profile dialog only opens by itself at start up.
* The output panel (`app.ui.OutputPanel`) is a `JTabbedPane`: an Application tab and one tab per open connection (profile name, server icon), added and removed by `MainController.addConnection/removeConnection`; `ConnectionWindowController.activate` brings the connection's tab forward with `setSelectedComponent`, never taking the focus. Each tab is a read-only `RSyntaxTextArea` with SQL colouring (`ui.editor.EditorTheme`, same theme as the query editor) with its own cap and a `ui.editor.FindBar`.
* `ui.editor.FindBar.install(area, host)` puts a find bar at the bottom of a `BorderLayout` host and binds menu key+F: RSyntaxTextArea's `SearchEngine`/`SearchContext` (mark all, wrap), Enter next, Shift+Enter previous, Match case, Esc and the cross close it and return the focus to the text; "n of m"/"No results" comes from the pure `FindMatches`. The output tabs and the query editor use it.
* Clear (`OutputPanel.clear`: eraser button as the tabbed pane's trailing component, Clear in the text area's context menu, menu key+K in the log) empties only the text of the tab in front, disabled with "The output is empty." when there is nothing.
* The output panel does not wrap lines (re-wrapping a long log made resizing slow), keeps at most 200000 characters per tab, and the split pane uses continuous layout with `resizeWeight` 1.0.
* FlatLaf defaults of the application are set centrally in `settings.Appearance` as FlatLaf global extra defaults, so they follow the theme and survive a change of look and feel: thin flat split pane dividers, and a selected tab with a darker background and the accent underline also without focus. A tab that is opened is always put in front (`setSelectedComponent`). Split panes have no one-touch arrows.
* The status bar of the application shows the state with its light on the left and the server and account of the active connection on the right (`ConnectionWindowController.showStatusInfo`). Activating a work window or selecting a node of a connection calls `ConnectionWindowController.activate`. What a view did last is shown in the bar at the bottom of its `WorkFrame` (`ConnectionView.setStatus`): `ConnectionWindowController.setViewStatus` (a table loaded, a table list shown) gives it to the view tab (table data or list), tree actions (`setStatusDetail(text)`: schemas listed or created, opened in the designer) go to the output panel only, `setStatus(tab, text)` (`ConnectionWindowController.setStatusDetail(tab, ...)`, used by `QueryController` for its query tab) to a given window. A query tab's bar never repeats a result: each result tab has its own line (time, database, rows, duration), so the bar says only "Running...", the failed statement, or the count of statements when some returned no rows (`QueryController.summary`, empty when every statement had rows); a window without a message of its own (a fresh query or editor) leaves the bar empty; the paging buttons of the table data (`TableDataTab.getNavigationBar`) sit in the same bar.

### Logging and output

* log4j2 only, never `System.out`/`System.err`. `OutputPanelAppender` shows log lines in the output panel: a line with the log4j context key `connection` goes to the tab of that connection without a prefix, other lines to the Application tab, and a line of a connection without a tab (failed to connect, closed) to the Application tab with `[profile]` in front (`app.OutputRouting`, pure, `OutputRoutingTest`). The key is set as follows: threads of a connection open `ConnectionWindowController.logContext()` in try-with-resources (`inBackground`, connecting, the query and completion threads), and `activate` sets it on the event thread for the connection the user works with (cleared when that connection closes); failures reported by `inBackground` and the connect thread are reported inside `logContext()`, so a connection's errors are in its tab. Export and import threads do not set it yet. Query text is logged at `debug` in `nl.errorsoft.esql.jdbc`.
* Log connection start, server product/version and driver, so the output explains what happened.
* Stack traces go only to the rolling log file `esqlmanager.log` in `DataDirectory.logs()` (`~/.esqlmanager/logs`, system property `esql.logs` elsewhere; surefire sets `target/logs`): appender `File` in `log4j2.xml`, daily or at 10 MB, 5 old files kept. The console and the output panel layouts have `alwaysWriteExceptions=false` (`OutputPanelAppender.layout`), so they show one line per event. Help > Open log folder (`Browsers.openFolder`).

### Errors

* Services and repositories do not swallow exceptions, they throw. A problem the user can fix (a row that can't be identified, a feature the database does not have) is an `EsqlException`, anything else is unexpected.
* The controller or window that handles a user action catches and calls `ApplicationContext.get().errors().report(parentWindow, "Drop table", e)`. That logs the error once (`ErrorHandler.log`: an `EsqlException` as "Drop table: <message>", an unexpected one as "Drop table failed: <cause> (details in esqlmanager.log)" with its stack trace for the log file only, `ErrorLoggingTest`) and shows one message with the ERROR icon, "Drop table failed: <cause>" (an action that already says "error" gets no "failed"). Report titles are verbs a user knows ("Load table", "Run query"). Do not call `log.error` and show a dialog yourself.
* Every dialog goes through `ui.dialog.Dialogs`: `info`, `warn`, `error`, `confirm` (QUESTION), `confirmDestructive` (WARNING, for dropping and deleting), `input`, `form` and `askSave`. Never `new JOptionPane()` or `JOptionPane.show...` elsewhere, and no `showMessage`/`showErrorMessage` copies in windows. A confirmation names the object and what happens ("Drop database 'shop' and all its tables? This cannot be undone.") and its button is the action ("Drop") next to Cancel. No success popup when the status bar or the window already shows the outcome.
* Long running jobs (export, import) report through `ProgressListener.failed`.
* Configuration files: `Settings` falls back to the defaults when settings.xml cannot be read, copies it to settings.xml.bak first and hands the problem out once (`takeLoadProblem`, reported by `MainWindow`); `saveSettings` throws. `ConnectionProfile` throws an `EsqlException` from every use when profiles.xml cannot be read (so it is not overwritten) and `getProfiles` skips a profile whose server type `ProfileXml.read` refuses (`ServerType.isKnown`). `ServerType.getDataTypes` throws when datatypes.xml cannot be read; `DatabaseDriver.getDatabaseDrivers` skips a bad driver.xml entry with a warning. `Main` installs `report` as the uncaught exception handler.
* A catch that stays silent has a comment saying why (for example a table that can't be counted is still listed).

### Resources and threads

* Everything `AutoCloseable` is opened in try-with-resources: result sets, statements, streams, and `DatabaseConnection` itself. `DatabaseConnection.executeQuery` closes its statement when the result set is closed.
* Background work (export, import, the process list, connecting and listing the databases of a new connection, running query statements) runs on virtual threads (`Thread.ofVirtual()`). The splash and the credits use a `javax.swing.Timer`. Swing is still only touched on the event thread. A controller runs the JDBC work of a user action with `ConnectionWindowController.inBackground(action, status, work, done)`: the work on a virtual thread with the status light saying what loads, `done` on the event thread, a failure reported once with the main window as parent (loading what is below a node expanded in the explorer, table data and paging, editing, inserting and deleting rows with the grid disabled, Indexes and Edit table tabs with their Save disabled while saving, table maintenance; the overload with an `always` callback enables the controls again also after a failure). The user manager dialog does the same with its controls disabled while loading. The generate dialog takes a snapshot of the model on the event thread (`Model.toDesigned()` gives a `designer.DesignedModel`), checks it with `designer.ModelCheck` (pure, `ModelCheckTest`) and generates it through `designer.control.GenerateController`.

### Java language level

* Java 25 idioms: records for plain data and parameter objects, pattern matching for `instanceof` and `switch`, switch expressions, text blocks for SQL, lambdas instead of anonymous classes, diamond operator. `java.util.Observable` is gone, progress goes through `ProgressListener`.

### Configuration and resources

* All XML files (settings, profiles, drivers, datatypes, .edm models) are read and written with the DOM and Transformer of the JDK behind `xml.XmlFiles`, never with a library and never with a `PrintWriter`. Reading refuses a DOCTYPE (no external entities) and has secure processing on. Writing is UTF-8 with tab indent and atomic (temporary file in the same directory, then move), so a failed write keeps the old file. Text with a character XML cannot store (control characters) is rejected with an `EsqlException`, not changed. Every failure is an `EsqlException` naming the file; `XmlFiles.backup` copies an unreadable file to `<name>.bak` (Settings). Call sites use its child/attribute helpers (`child`, `children`, `childText`, `addChild`, `setChildText`).

* The version in the title bar and splash comes from the pom, the commit from `git-commit-id-maven-plugin`; both are written to `build.properties` by resource filtering (`app.BuildInfo`). A build with uncommitted changes shows `-dirty` after the hash, without git the commit is `unknown`. There is no build counter.
* `runtime/` is the working directory: `conf/` (profiles, drivers, datatypes, settings), `credits.txt`. Code reads `conf/...` relative to the working directory, also in tests (surefire `workingDirectory`).
* `runtime/conf/profiles.xml` must not contain passwords or local test profiles when committed. Running the application rewrites it (`lastUsed`), so `git checkout runtime/conf/profiles.xml` before committing.
* JDBC drivers come from Maven Central, no jars in the repository. Only PostgreSQL (BSD-2) and SQL Server (MIT) are bundled. MySQL (GPLv2 with FOSS exception) and Oracle (FUTC) are downloaded on first use by `driver.DriverService` into `DataDirectory.drivers()` (`~/.esqlmanager/drivers`, system property `esql.drivers` overrides it) at the version and SHA-256 pinned in `driver.DriverArtifact` (the trust anchor; checked on download and before the jar is loaded, a mismatch is deleted and is an `EsqlException`; the class loader reads a private temporary copy of the checked bytes). Which artifact a server type needs is `ServerType.driverArtifact`. A jar is loaded by its own `URLClassLoader` once per run, again when the file's time or size changed. `DatabaseConnection.connect` connects through `DriverService.connect`, which uses the `Driver` that `load` returns (never `DriverManager`, which hands out the first registered driver that accepts the URL; a driver that returns null is an `EsqlException`); `ServerType.driverSource()` says where it comes from (own jar from `<driverJar>` in driver.xml, bundled, or downloaded). `driver.control.DriverDownloadController.ensureDriver` asks before connecting or testing a connection; a jar is downloaded once at a time. MySQL stays a test-scope dependency for the contract tests. Upgrading a downloaded driver means changing the version, size and SHA-256 in `DriverArtifact` (compare with the `.sha1` on Central).
* The user documentation is Markdown in `docs/` (index.md, getting-started.md, tables-and-columns.md, query.md, designer.md, settings.md), with its images next to it. Maven copies `docs/*.md` and `docs/*.png` into the jar under `/docs`; `help.HelpPages` renders a page with commonmark (+ GFM tables) to HTML 3.2 friendly HTML and `help.ui.HelpPanel` shows it in the help window (links to .md pages stay in the pane, http(s) links open in the browser). Update these pages when a feature changes.
* Images and `log4j2.xml` are in `src/main/resources`. Images are loaded through `ImageLoader` (cached, paths relative to the classpath root).
* Icons are Lucide SVGs in `src/main/resources/icons/svg` (ISC license, `NOTICE.txt`), drawn with FlatLaf's `FlatSVGIcon` so they follow the theme. A new icon is a stroke `#6e6e6e` SVG plus an `images.addIcon(name, file, size, selected)` line in `ApplicationContext.imageLoader()`; callers use `imageLoader().getIcon(name)`, never `new ImageIcon(...)`. The tree uses a `...sel` variant (selection colour) for selected rows. Brand icons (`addBrandIcon`) keep their colour, are lightened on dark themes and have a white `...sel` variant for selected rows. The application logo is `icons/logo.svg` (own artwork), rendered by `ImageLoader.logoImages()` as the window icons and the macOS Dock icon (`java.awt.Taskbar`), and by `ImageLoader.logoIcon(size)` on the splash. There are no GIFs. Server logos are Devicon (MIT) and Simple Icons (CC0) SVGs (trademarks of their owners) named `brand-<slug>.svg`, filled with the brand colours and registered at 18px with `images.addBrandIcon` (keeps its colour when selected, lighter on a dark theme). `ServerType.iconName()` is the only place that maps a server type to its icon; the profile lists (`connection.ui.ServerIconRenderer`), the connection window's frame icon (shown in its window tab) and the server node of the tree use it.
* There is no licensing, registration or auto-update any more; do not reintroduce them.

### Code style

* Formatting is done by Spotless with the Eclipse formatter profile in `.eclipse-formatter.xml` (Java conventions: braces at the end of the line, tabs, 160 columns, LF line endings; if, else, for and while always have braces). Run `./mvnw spotless:apply` before committing, `./mvnw verify` runs `spotless:check` and fails on unformatted code. `.editorconfig` holds the same basics for editors. IntelliJ's own formatter does not follow it.
* Resources are closed with try-with-resources. No deprecated API in new code (`new Integer`, `Dialog.show()`, ...).
* No em-dashes in prose or documentation.

For logic, behaviour or enablement changes check light only, or state that nothing visible changed. Docs images stay light only.

Look at the result, check icons, alignment and the status bar.

## Tests

* `DialectContractTest` runs the same scenarios against every dialect: create and alter tables, indexes, export and import, editing data with hostile text, user management, creating databases. `PostgresDialectTest` and `MySqlDialectTest` supply the container. A new dialect gets a subclass.

## Architecture

The code is moving from layers by technical type (`gui`, `control`, `domain`, `data`) to packaging by feature. The target:

* Package by feature (functional packaging), for example `connection`, `database`, `table`, `exporter`, `importer`, `server`, `designer`, `user`, `query`.
* Inside each feature the layers are strictly UI -> Controller -> Service -> Repository. Dependencies point downwards only.
  * UI (Swing): no business logic, no JDBC. Swing classes only in UI packages.
  * Controller: translates UI events into service calls and shows the outcome. It gets its service from `connectionWindowController.getContext()`.
  * Service: application logic (order of steps, validation, updating the domain objects after a change). Calls repositories, never SQL.
  * Repository: the only place that runs SQL. It extends `jdbc.AbstractRepository`, which holds the connection and gives `dialect()`, `quote()`, `literal()`, `useDatabase()`, `executeUpdate()` and `executeAll()`. A repository asks the `Dialect` for everything that differs per server and never branches on the server type.
* Domain types (`Table`, `TableColumn`, `TableIndex`, `TableCell`, `DatabaseUser`, ...) are plain data without a connection.
* A result that is more than one object is a small record in the feature package (`table.QueryResult`).
* Do this one feature at a time and keep the contract tests green.

Features and their packages (all under `nl.errorsoft.esql`; each has `control` and `ui` subpackages where it has windows):

* `table`: tables, columns, indexes, rows (`Table`, `TableColumn`, `TableIndex`, `TableCell`, `TableService`, `TableRepository`, `QueryResult`).
* `database`: databases, their schemas and table lists (`Database`, `Schema`, `DatabaseService`, `DatabaseRepository`), including the tree view.
* `exporter` and `importer`: SQL export (`ExportService`, `ExportRepository`, `ExportOptions`) and import (`ImportService`, `ImportRepository`). Services run on their own thread and report progress to a `job.ProgressListener`; `job.ui.dialog.ImportExportProgressDialog` shows it for both. What is exported, or imported into, is a sealed `job.ScriptTarget` (`OfDatabase`, `OfSchema`, `OfTable`; `ScriptTarget.of(node)` throws `EsqlException` for any other node); an import without a target runs in the database the connection uses.
  * Schemas: exporting a database on a dialect with `Feature.SCHEMAS` takes the tables of every schema (`ExportRepository.tableNames`), statements name `schema.table` and the script starts with `Dialect.createSchemaIfMissingSql` for each schema. Importing into a `Schema` (or a table of one) switches with `DatabaseConnection.useSchema` (`Dialect.useSchemaSql`, `SET search_path` on PostgreSQL) and restores the previous schema afterwards. Contract tests: `exportOfADatabaseRestoresEverySchema`, `importIntoASchemaPutsUnqualifiedTablesThere`.
  * Export switches the shared connection to the database of each part (`ExportRepository.readFrom`) before the part and before each table and view, because listing the targets and the query tabs move it (contract tests `exportOfTwoDatabasesReadsEachFromItsOwnDatabase`, `tableExportReadsTheTablesDatabaseWhateverTheConnectionUses`). Metadata pattern arguments (`getColumns`) escape `_` and `%` with `getSearchStringEscape()`.
  * The export and import windows read their tree in the background before they open (`DatabaseController.treeStart`: the databases and the children on the way to the node selected in the explorer, when it belongs to that connection, `ConnectionWindowController.selectedObject`), then build it and open it at that node on the event thread (`databaseTree`, `selectInTree`). A node opened later loads its children in the background (`DatabaseController.children`: schemas of a database on servers with schemas, else tables; tables of a schema) and `showChildren` puts them in the tree.
* `blob`: uploading and saving binary cells (`BlobService`, `BlobRepository`).
* `user`: accounts and privileges (`UserService`, `UserRepository`). The SQL itself is written by the dialect's `UserAdmin` and run by the repository. Changing privileges is planned first (`UserService.planGrants` returns a `GrantChange` with the current and wanted privileges and the statements), the dialog confirms `revoked()` of that plan and `applyGrants` runs exactly its statements. MySQL's `GRANTEE` is `'name'@'host'` without escaping, the contract test `grantsWorkForAUserWithAQuoteInTheName` covers a name with a quote.
* `designer`: the model designer. The `Designed*` records (`DesignedDatabase`, `DesignedTable`, `DesignedForeignKey`) are the input of the generation, the canvas model is `designer.model.ModelForeignKey` and `designer.ui.diagram.DesignerColumn`. `DesignerService` creates the designed databases and tables from `DesignedDatabase` and `DesignedTable`, then adds each table's `DesignedForeignKey`s in a second pass (skipping keys that exist, checking that the columns exist) through `TableService.addForeignKey`. Reading a database back keeps only keys on tables of the same schema and database (`DesignerRepository.loadForeignKeys` compares `PKTABLE_CAT`/`PKTABLE_SCHEM`).
  * The model links a table to its database with a generic reference (`Model.addReference`, never table-to-table). Foreign keys are separate: `designer.model.ModelForeignKey` records in `Model` (`addForeignKey`, `foreignKeysOf`), removed with their table and kept in step with renamed or removed fields (`Model.fieldsEdited`, called by `TablePropertiesPanel`).
  * Model files (.edm) are read and written by `designer.model.ModelXml` through `XmlFiles`. New files are version 0.3 (with `<foreignkeys>` and `<servertype>`, the `ServerType` number, empty when unknown), 0.1 and 0.2 files still load with an unknown server, missing sections mean empty. `ModelPersistenceTest` has a 0.1 fixture in `src/test/resources/designer`.
  * A `Model` knows the `ServerType` it is designed for (null when unknown): `DesignerCanvas.setServerType` (from the `DesignerWindow`'s connection) gives it to new models and to a model without one, `ConnectionWindowController.openDatabaseInDesigner` sets it on the model read back. `Model.term()` is `Dialect.databaseTerm()` of that server ("database" while unknown); the database card, the canvas menus and toolbar and `ObjectNames` take the word from it. A database card is a database on every server, also on PostgreSQL (`DesignerService.generate` creates the database and the tables in its current schema), so the word is "database" everywhere today. `DesignerWindow.generate` only generates on a connection of the model's server (`designer.ModelTarget.refusal`, pure, `ModelTargetTest`): its own connection when it matches, else a chosen open one; a model without a server adopts the connection's. `ModelForeignKey.validate(Model)` refuses a key between tables linked to different database cards ("A foreign key can only link tables of the same database."), `ForeignKeyDialog` uses it.
  * Foreign key SQL comes from `Dialect.addForeignKeySql(TableName, TableForeignKey)`/`dropForeignKeySql`; actions are checked against the whitelist `Dialect.REFERENTIAL_ACTIONS`. `Dialect.checkForeignKeyTable` refuses MySQL tables that are not InnoDB.
  * Look: objects are cards painted by themselves (`TableCard`, `DatabaseCard` as a pill, `NoteCard` as a note) with colours and fonts from `designer.ui.diagram.DesignerTheme` (UIManager keys, so light and dark both work). A component is larger than its card by `DesignerTheme.SHADOW` for the shadow; `ModelCard.cardBounds()` is the card in viewer coordinates, `contains` only accepts the card, and model files store the card position (`setCardLocation`). The table header shows the storage engine only when the server's dialect has table types (`DesignerCanvas.setShowTableTypes`). `DesignerCanvas` paints the canvas with an optional dotted grid (View > Show grid).
  * Relations are drawn by `designer.ui.diagram.ConnectorPainter` below the cards: a foreign key is an orthogonal connector with rounded corners from the child's column row (`TableCard.rowAnchorY`) to the parent's, a crow's foot at the child and a double bar at the parent, around the right side when the cards overlap horizontally or for a self reference. Hit testing uses an 8px stroked shape. Database and note links are dashed curves.
  * Foreign key UI: drag from the field icon of a row onto a column of another table (a ghost connector follows the mouse; `Model.mouseDragged` does not move a table when the drag starts on a field icon), a table's context menu "Add foreign key...", or the Foreign Keys tab of `TablePropertiesPanel`. All open `ForeignKeyDialog`, which checks the key with `ModelForeignKey.validate()` (columns exist, types of the same kind, allowed actions) and reports problems through the `ErrorHandler`. Double click on a connector edits it, Delete or its context menu removes it. Shift-drag still links a database or a note. The Foreign keys tab of `TablePropertiesPanel` edits a copy of the table's keys (Remove asks with `confirmDestructive`); `saveProperties` puts them in the model before `Model.fieldsEdited`, Cancel leaves the model alone.
  * The designer's menu items (`DesignerWindow`, the Model menu of `DesignerCanvas`) use action listeners, so their accelerators (menu key + N/O/S/A/D, Delete, F1-F5) and mnemonics work from the keyboard; there is no global AWT key listener. `DesignerCanvas.deleteSelection` removes the selected connector or else the selected cards.
  * Reverse engineering: "Open in designer" (database context menu and explorer toolbar, enabled for a database or schema node) calls `ConnectionWindowController.openDatabaseInDesigner`. `DesignerService.reverseEngineer(Database)` (the current schema) or `reverseEngineer(Schema)` (a schema node) returns a `DesignedDatabase` with every table (views left out, `DesignerRepository.loadTableNames` asks the metadata for type TABLE), its columns, primary key (composite too), single column indexes as the column's index/unique flags, and the foreign keys between tables of that database (`getImportedKeys`, NO ACTION as empty). `Dialect.readColumn` turns a `getColumns` row into a `ColumnDefinition` with the type names of `datatypes.xml` (PostgreSQL `int4` becomes `integer`, serial and identity columns become auto increment, `'x'::character varying` becomes `x`; MySQL strips `UNSIGNED` into the flag). `designer.ui.diagram.ModelFactory.fromDatabase` turns the records into a `Model`, `DesignerWindow(mainWindow, connectionWindow, model)` shows and arranges it. Generating it again skips what exists. Contract test: `designerReadsAnExistingDatabaseBack`.
  * Layout: `designer.layout.AutoLayout` (no Swing, sizes and edges in, positions out) uses the layered algorithm of the Eclipse Layout Kernel (`org.eclipse.elk.alg.layered`, direction right), so a referenced table is left of the tables that refer to it; tables without relations (or only a self reference) go in a grid below. ELK needs `LayoutMetaDataService.registerLayoutMetaDataProviders(new LayeredMetaDataProvider())` outside Eclipse and the undeclared `org.eclipse.xtext.xbase.lib`; Guava is pinned because ELK asks for any version. `CONSIDER_MODEL_ORDER_STRATEGY` keeps the input order within a layer, so the referenced tables follow the order of the key columns. `ModelArranger.arrange(Model)` puts the databases in a row at the top and the tables below with it (View > Arrange automatically). `AutoLayoutTest` checks overlap and order.
  * Exports: `designer.export.DiagramExporter` writes a `DiagramModel` (plain records made from a `Model` with `Model.toDiagram()`; the `designer.export` package has no Swing imports) as PlantUML or Mermaid text, without Swing (File > Export as PlantUML/Mermaid).
* `designer.ui.diagram` holds the canvas (`DesignerCanvas`, the cards `ModelCard`, `TableCard`, `DatabaseCard`, `NoteCard`, `ConnectorPainter`), `designer.ui` also `ModelFileFilter`, `designer` the Swing-free `FieldRules` and `ModelCheck`, `designer.ui.dialog` the property, foreign key, history and generate dialogs, `designer.ui` the window (`DesignerWindow`, a `JInternalFrame` on the desktop of the main window, never a separate OS window; `MainWindow.addDesignerWindow` gives it a window tab, maximized like the work windows; `MainController.activeConnection` returns the designer's connection when a designer is in front; closing asks to save, disconnecting detaches it (`MainWindow.detachDesigners`); its menu bar stays inside the frame, also with the macOS screen menu bar).
* `query`: statements typed by the user (`QueryService`, `QueryRepository`, `SqlScript`, `SqlContext`). `QueryService.execute` runs any statement with `Statement.execute` and returns an `ExecutionResult` (`Rows`, `Updated`, `DatabaseChanged`), so WITH, EXPLAIN, VALUES, TABLE and commented queries show rows; a database switch written the server's way (`Dialect.databaseSwitchTarget`: `USE db` on MySQL, `\connect db` or `\c db` elsewhere) goes through `DatabaseConnection.useDatabase` (on PostgreSQL `USE db` is not a switch and is sent to the server as typed). The query tab with syntax highlighting and completion (`ui.QueryTab`, `ui.SqlCompletionProvider`, `control.QueryController`).
  * Explain (`Feature.EXPLAIN`, PostgreSQL and MySQL; the buttons are hidden elsewhere): `Dialect.explainSql(statement, analyze)` writes `EXPLAIN (FORMAT JSON)` / `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` on PostgreSQL and `EXPLAIN FORMAT=JSON` / `EXPLAIN ANALYZE` (tree text, queries only) on MySQL. `QueryRepository.explain` returns the raw rows (`query.QueryPlan`), `QueryController.explain` parses them on its thread with `query.plan.PlanParser` (pure, recognises the shape, never the server type; `JsonReader` is its own small JSON reader) into a `Plan` of `PlanNode`s (`Estimate`, `Actual` with the time of all loops, `Buffers`, conditions, details). `PlanHints.of(node)` gives the neutral hints, `Plan.share`/`hottest` the weight (exclusive time when analyzed, else exclusive cost; MySQL prefix costs are turned into each table's own part). `query.ui.PlanView` shows it (tree table `PlanTableModel`, bars and markers painted in `Forms.warningColor()`/`Component.accentColor`, details pane, Text tab with Copy plan). Analyze of a statement that is not read only (`QueryPlan.isReadOnly`) is confirmed with `confirmDestructive`. Tests: `PlanParserTest` on plans captured from both containers in `src/test/resources/query/plan`, `QueryPlanTest`, contract test `explainShowsThePlanAndAnalyzeRunsTheStatement`.
* `connection`: profiles, drivers, server types, the explorer, the work windows (`WorkFrame`, `WorkFrames`) and `ConnectionContext`; the connect dialog's picker is `connection.ui.DatabasePickerPanel`.
* `server`: process list, server status and variables (`ServerService`, `ServerRepository`, `ServerProcess`). `server.control.ProcessListController` opens its own connection, refreshes on a virtual thread and kills processes; `server.ui.dialog.ProcessListDialog` only shows the rows and the countdown.
* `app`: main window, credits, splash, start up, `OutputPanelAppender`. `settings`: `Settings`, `Appearance` and `settings.ui.dialog.SettingsDialog`.
* `ui`: Swing parts shared by several features: `ui.icon` (`ImageLoader`, `StatusLight`), `ui.table` (`ColumnWidths`, sortable headers, `MultiLineCellEditor`), `ui.editor` (`EditorTheme`), `ui.component` (`CheckBoxTree`, `EditorTab`), `ui.util` (`Browsers`, `Forms`, file filter).
* `jdbc`: `DatabaseConnection` and `AbstractRepository`. `dialect`: `Dialect`, `AbstractDialect`, `DialectFactory`, `UserAdmin`, the statement records `MaintenanceStatement` and `GrantQuery`, with `mysql`, `postgres`, `sqlserver` and `oracle` sub packages. `error`: `EsqlException` and `ErrorHandler`. `job`: `ProgressListener`. `ColumnDefinition` and `DataType` are in `table`.
* `app.ApplicationContext` (singleton, `ApplicationContext.get()`) is where components are resolved from. It holds what exists once per application (`imageLoader()`, `settings()`) and one `connection.ConnectionContext` per open connection (`connection(databaseConnection)`, released when the connection closes). Do not pass an `ImageLoader` or `Settings` through controllers.
* `ConnectionContext` creates every repository and service of one connection once and wires them with constructor injection. Services are per connection because several connections are open at the same time, so they are never application singletons. Controllers get a service from `connectionWindowController.getContext()` (`getContext().tables()`, `.databases()`, `.users()`, `.servers()`, `.queries()`, `.designer()`) and never create services or repositories themselves. A service receives its repository and the services it needs in its constructor (`BlobService` uses `TableService.rowFilter`). Jobs that report progress to observers (export, import, blob transfer) are created per run with `newExport`, `newImport` and `newBlobTransfer`. A new feature adds its repository and service to `ConnectionContext`.
* Parameters that belong together are a record (`ExportOptions`, `DesignedTable`, `table.TableDefinition` for creating a table and its preview, `connection.DriverProperties`), not a long argument list. `TableService.addColumn` and `editColumn` take a `ColumnDefinition`; a `DataType` holds the column options it allows as a set of `DataType.Option` (`allows(Option)`, `DataType.named` for a type without options).

## Known technical debt

* PostgreSQL schemas: user manager table grants ignore schemas, Open in designer on a database node reads its current schema (a schema node reads that schema).
* SQL Server and Oracle dialects only browse; their DDL, user management and maintenance are not implemented.
